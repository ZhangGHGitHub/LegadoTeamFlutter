## 1. 计划结论

重构已经形成可工作的 Rust 核心 + Flutter UI 主链，不需要推倒重建 Provider、BookApi 或 FFI 分层。当前问题是完成度口径和证据分散：一部分已实现且有回归的能力仍留在开放项里；部分汇总说已闭环的 UI 屏逐行却仍缺参考截图或状态覆盖；真机/外部素材验收与代码缺陷又混在同一份历史表中。

因此建议按以下顺序推进：

1. **先建立可信的当前状态**：逐项比对 HEAD、关闭提交、测试、设备或素材证据，修复计划与台账矛盾。
2. **优先消除可导致错误数据、卡死或进度丢失的阅读主流程风险**：核销 B-10/B-11、搜索聚合路径与缓存清理语义；确认问题存在后才修，不把旧登记直接当缺陷。
3. **按用户已确认的全域视觉基准补齐浅色与深色屏幕证据**：先完成缺采清单和暗色基线，再逐屏修差异。
4. **以书源真实命中为依据补高价值兼容能力**：从 916 源扫描候选中排序，不追求机械地复制完整 JVM/Android API。
5. **把依赖用户素材、网络或硬件的端到端验收单独管理**，不可用单测或模拟器冒烟代替。

## 3. 需求范围与优先级

### P0：正确性、证据可信和可交付性

1. 统一状态枚举：`已实现待复验`、`已验证关闭`、`核验中`、`代码缺陷待修`、`待用户素材`、`平台限制/N/A`、`用户决策待定`。
2. 每项绑定代码落点、首次发现/最近证据日期、HEAD 或提交、验证命令/测试名、外部阻塞、下一动作及责任轨道。
3. 核验 B-10、B-11、搜索聚合 P2-20、书架占位能力；B-13 更新为已有后续修复证据，需核销范围而非继续重复排期。
4. 阅读主流程回归覆盖开书、空目录、目录刷新、正文缓存、换源成功/失败/取消、快速翻章、后台保存、退出重进、缓存清理。
5. 每个已确认缺陷先构造能复现的回归测试或稳定设备步骤，再修代码。

### P1：用户可见的一致性与兼容性

1. 重新对账浅色 43 屏台账，并按空/有数据、加载/失败、选择/菜单、必要的正文状态拆分屏状态。
2. 建立全域深色屏基准。优先高频核心屏，之后覆盖其余屏和二级页面；参考截图未采集前不能把颜色差异凭主观猜测改成完成。
3. 搜索多态结果和分页/取消体验，核对 Rust 聚合、Dart 增量路径与契约的精确边界。
4. 对常用书源宿主能力按真实源数排队，先处理高命中且能离线夹具化的能力；明确哪些 Android/JVM 特有 API 是有意不支持并给出可理解的失败反馈。
5. 修订 `TWO_TRACK_DEV_SPEC.md` 与 `rust/PROGRESS.md` 等过时协作/状态说明，使其与当前 AGENTS、API 契约、Windows 工具链和视觉基准一致。

### P2：长尾、外部条件和技术债

1. localhost 网络差分矩阵：重定向后最终 URL、相对分页、charset/BOM/meta、retry/body replay、cookie 域、代理绕过、配置刷新。
2. MCP/Server 工具逐入口检查真实数据路径与错误码，归档旧“桩实现”口径。
3. 素材到位后验收 WebDAV、音频、媒体键、漫画/视频、ruleReview、皮肤 zip、验证码/倒计时/外链等真实链路。
4. 评估 iOS/桌面后台、WebView 与存储行为的跨平台差异；先做边界盘点，不预先承诺大范围平台重写。

### 明确不纳入本轮计划

- 不重建 Flutter Provider/BookApi 架构，不迁移 FFI 复杂对象传输策略。
- 不把 916 源扫描中每个失败自动转成新功能，不补齐完整 JVM/Android 模拟层。
- 不增加 Android 原版不存在、且未经用户授权的功能。
- 不删除 Android 原版双轨代码，不进行未经批准的 DB 破坏性迁移。
- 不以“零 TODO/零桩/全功能完成”作为目标；只按有范围的证据关闭任务。

## 5. 每个重构批次的详细执行流程

### 5.1 立项与证据登记

1. 从 `docs/REFACTORING_ACTIVE_PLAN.md` 唯一开放队列领取任务；本方案获确认后，把选定的阶段拆为该计划内的编号事项。
2. 记录用户现象或差异、原版源码路径/符号、重构版路径/符号、相关参考版视觉材料（仅 UI）、首次发现版本、当前 HEAD、受影响平台、风险级别。
3. 先查历史关闭提交与测试证据。证据过期或范围不符时标为“待复验”，禁止重复实现。
4. 明确本批非目标与用户可观察行为；若涉及新 API，先写 `API_CONTRACT.md` 的签名/输入/输出/错误语义/Mock 示例。

### 5.2 复现与方案评审

1. 优先写最小回归测试，确认它在当前实现中确实失败；设备问题用稳定的步骤和屏幕/DB/log 证据替代推测。
2. Rust 侧区分纯逻辑单测、DB 事务/迁移测试、loopback 网络测试、JNI/FFI 运行时测试；Flutter 侧区分 unit、widget、integration 与设备视觉复验。
3. DB 改动先审查旧数据兼容、迁移幂等、备份与失败回滚。不可逆迁移必须单列影响说明，不得偷偷并入一般功能批次。
4. QuickJS/Parser 改动用最小规则样本加已有书源 fixture；网络/站点现象先剥离第三方可用性。
5. 跨模块、FFI、公共 API 或大范围重构，在编码前冻结范围和回滚点，并在提交前取得 `code-reviewer` 结论。

### 5.3 实施与同步

1. 一个提交批次只处理同一根因或紧密依赖的一组差异，避免同时改 UI 视觉、解析语义和 DB schema。
2. 纯 UI 先由 Mock 驱动；Mock 的空数据/占位数据不可作为 Rust 正确性的证据。
3. FFI 必须契约先行，随后 BookApi、RustApi、MockBookApi、Rust 导出、FRB 双侧生成代码和原生库按原子流程同步；禁止手改生成文件。
4. 视觉修改走主题槽位与参考截图，不散落硬编码色值；多态屏的各状态分别验收。
5. 限定 diff 到立项路径；任何发现的超范围问题另开 ID，不顺手扩散改动。

### 5.4 验证、验收、交付

1. 先跑最小测试，再跑对应轨道门禁；普通 Flutter/Rust CI 覆盖的验证以 CI 结果为准，不另派角色重复跑同一门禁。
2. 设备验收仅在本批涉及 UI/真实生命周期/无法由 CI 覆盖时执行；先检查设备当前状态、端点、网络、分辨率、包和 debug/release 变体。
3. UI 屏提供同状态、同尺寸参考/我方截图与逐项差异结论；行为问题提供测试或 DB/日志记录。
4. 版本、CHANGELOG、应用内更新日志和进度台账按项目规则同步；验证通过后本地提交，提交正文写根因/来源证据。高风险改动先评审再提交。
5. 更新状态必须写证据路径、命令或测试名、HEAD/提交和剩余限制。失败时登记真实阻塞和复现条件，不以“已执行”代替“已通过”。

## 6. 跨领域专门流程

### FFI 与契约

需求登记 → 双轨确认语义与错误模型 → 更新 `API_CONTRACT.md` → Mock 先行 → Rust API/实现 → FRB codegen 一次生成 Dart/Rust → 编译目标 native library → hash/契约测试 → Flutter + Rust CI → 真实 DLL/SO 路径验证 → 更新契约统计和台账。任何一步失败都保留上一个已知可运行契约与二进制组合。

### 数据库与缓存

确认 schema 影响 → 用旧版 DB fixture 复现 → 设计事务和迁移 → 验证新装/升级/重复打开/中途中断恢复 → 断言数据、进度、缓存键与外键 → 验证备份恢复和失败路径 → 记录不可逆边界。清缓存类需求同时核对 UI 状态、内存状态、DB 行和重新开书行为。

### 阅读与搜索状态机

枚举状态和触发序列 → 检查并发代数/取消 token/生命周期 → 对重复请求、快速翻页、刷新中换源、取消后重试做交错测试 → 验证保存与重进 → 最后做设备复验。搜索另外区分单次聚合与跨页会话状态，避免把两种去重边界混为一谈。

### UI 一比一

建立屏幕×状态矩阵 → 采参考端同分辨率截图 → 采我方当前版本 → 逐维记录布局/层级/间距/形态/图标文案/颜色字体/状态 → 修复 → 同条件复拍 → 逐项关闭或记录保留差异。暗色基准未采到时标“待采集”，不得根据浅色反推暗色目标。

### 书源/规则能力

从真实规则扫描确定候选 → 选取离线 JSON/HTML/JS fixture → 对照原版 Kotlin 对应符号或稳定响应 → 单能力实现 → 运行 parser/QuickJS 测试及影响源回放 → 检查性能和安全边界 → 记录平台专属的不支持项。每次新增能力注明“命中源数量、救活源数量、回归样本、未覆盖语义”。

## 7. 风险与缓解

| 风险 | 影响 | 缓解和退出条件 |
|---|---|---|
| Active 计划与 parity 台账过时或互相矛盾 | 重复开发、错报完成 | 阶段 0 先对账；任何绝对完成数字必须带屏/状态范围和证据日期。 |
| 模拟器网络/ADB 状态漂移 | 设备任务白跑或错误归因 | 每次设备任务先探测 MuMu 在线实例、端点、guest 网络和目标包；当前不可用则记录阻塞，不改用已废弃雷电档。 |
| FFI 改动破坏生成物与 native hash 同步 | 启动失败/运行时异常 | 契约优先、双侧 codegen 与 native 构建原子化，运行 hash 校验和真实桥接测试。 |
| 页面视觉修复无参考暗色基准 | 错误颜色决策、回归 | 先采参考截图；无素材屏不得标视觉闭环。 |
| 真实书源依赖网络/登录 | CI 不稳定、结果不可复现 | CI 用固定 fixture/loopback；真实网络作为独立验收，不把软失败统计成缺陷或通过。 |
| DB schema 或缓存清理伤及用户数据 | 进度/章节丢失 | 升级 fixture、事务测试、备份说明、迁移前后关键字段比较；迁移与行为改动拆批。 |
| 扫描候选被误当成需求 | 无授权扩功能和范围膨胀 | 以原版/参考版功能基准与真实命中证据做筛选，新增能力逐项确认边界。 |
| 外部素材迟迟不到 | 验收周期不可控 | 将代码交付与素材验收分开；明确请求素材、阻塞项和可先完成的离线测试。 |

## 8. 周进度和完成标准

每周只报告以下可核验字段：本周关闭 ID/证据；仍开放 ID 和当前阻塞；本周代码提交与 CI run；设备任务的实例/包/变体/截图路径；新增风险；下周单一首要目标。不要仅报“完成百分比”。

单项只有满足以下条件才能关闭：

- 源码实现位于明确路径，行为符合原版功能基准及已确认的视觉基准；
- 有与风险相称的自动测试或设备证据，CI 覆盖项以 CI 结果为准；
- 契约、Mock、生成物、DB migration、版本和文档已同步（适用时）；
- 没有未解释的数据丢失、错误吞没、无反馈等待、崩溃或兼容性回归；
- Active 计划状态、关闭日期、证据路径和剩余限制已更新；
- 外部素材未到位时只关闭工程项，验收状态仍保持“待素材”。
