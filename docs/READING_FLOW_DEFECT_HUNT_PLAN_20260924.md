# 阅读主流程缺陷猎捕计划（Reading-Flow Defect Hunt）

> 建立：2026-09-24 ｜ 依据：用户指令「继续修，然后请给出方案，让子代理尝试从多个方面寻找出，这种影响阅读主要流程的缺陷」
> 执行方式：**每波 ≤2 个子代理并行**（AGENTS.md 并行上限）；**猎捕代理只产出「带复现证据的缺陷清单」，不做修复**；修复由主代理分诊后另派（修复需回归证据 + 实机验证）。

## 一、阅读主流程定义（猎捕范围）

```
① 找书     书架 / 搜索 / 发现 / 书单 → 加入书架
② 开书     书架单击直达阅读（A4 对齐 B）/ 卡片长按 → 详情页 → 「阅读」
③ 目录     目录加载（本地命中 / 联网分页抓取）→ 章节定位 / 搜索章节
④ 读正文   正文抓取（缓存优先）→ 分页/滚动 → 翻章（上/下、章边界）→ 进度保存/恢复
⑤ 换源     单章换源 / 换书源（迁移目录 + 正文重取 + 进度映射）
⑥ 离线     缓存当前章 / 批量缓存 / 离线可读 / 缓存清理
⑦ 设置     字体/字号/行距/背景/翻页动画/简繁/替换规则（改后立即生效）
⑧ 退出重进 退出阅读 → 书架进度刷新 → 重进恢复位置
```

**判定为「影响主流程」的门槛**：能让上述任一步骤**卡住、等很久、显示错数据、静默失败、进度丢失、崩溃**，且用户可感知。

## 二、六个猎捕视角（每视角一个子代理任务书）

| 视角 | 方法 | 产出物 | 证据形态 |
|---|---|---|---|
| **A 状态机/生命周期（Dart）** | 逐个 notifier/provider 读取主流程路径（`reader_notifier`/`search_notifier`/`bookshelf_notifier`/`change_source_notifier`），找：缺 await 的导航、async gap 后用 context、dispose 后 setState、状态没随数据刷新（陈旧 currentBook/章节/缓存）、并发竞态、未捕获异常吞掉 | 缺陷清单（每条：现象/触发路径/文件:行号/最小复现） | **可复现的 widget/unit 测试**（先红）+ 修复建议；不允许只给推断 |
| **B Rust 数据链路（TOC/正文/缓存/进度）** | 审 `legado-ffi` reader/search/web_book + `legado-db` 缓存与进度路径：缓存陈旧/键错、进度读写语义（0 基/1 基）、分页抓取是否串行、超时与重试、空正文/越界/无目录的处理、DB 写序与事务 | 缺陷清单 + **耗时剖面**（各阶段 ms） | 单元测试（先红）+ 计时数据 + 关键代码路径引用 |
| **C 失败与边界（异常路径）** | 构造/模拟失败：网络中断、站点 404/500、源失效、目录空、正文空、书被删、DB 忙、存储满、进程被杀；核对「是否有可见提示 / 是否死等 / 是否丢数据」 | 缺陷清单（按用户可感知程度排序） | **失败注入测试或设备复现**（logcat/dump/DB 快照） |
| **D 真机主流程巡检** | 在 MuMu 真机按 ①→⑧ 走一遍完整流程，逐步骤记录：耗时、是否有提示、数据是否正确（DB 对照）、是否有异常；重点覆盖「慢/异常」路径 | 巡检记录表（每步：预期/实测/耗时/证据文件） | dump + 截图 + DB 快照 + logcat |
| **E 性能剖面** | 对每阶段计时（搜索首个结果、目录首屏、正文首屏、翻章、换源重载、缓存批量）；找出「超过阈值（如 >2s 无反馈）」的点并定位成因 | 耗时表 + 热点定位 | 计时日志/设备 stopwatch/DB 时间戳 |
| **F 平台差异（iOS/Android）** | 以 iOS 模拟器 e2e 为基座，找 iOS 特有的主流程断点（文件路径/WebDAV/TTS/后台/WebView 登录/网络栈差异） | 缺陷清单（iOS 侧） | iOS 模拟器 e2e 或 CI 证据 |

## 三、证据与分级规则（DoD 口径）

1. **每条缺陷必须带复现方式**：最小测试（先红后绿可验证）或设备复现步骤 + 证据文件（dump/截图/DB/logcat）；**子代理自述不构成依据**。
2. 分级：**【主流程阻断】**（无法完成某步骤 / 崩溃 / 丢数据）→ 立即修；**【主流程重扰】**（可完成但等很久 / 数据错 / 无反馈）→ 排期修；**【边缘】**（特例/观感）→ 登记。
3. 与既有台账去重：已登记项（如换源重载 ≈10 分钟、`totalChapterNum` 未同步、源名 emoji）不重复立项，猎捕代理需在清单里标注「已登记」并补充新的证据或扩展面。

## 四、波次排期（每波 ≤2 并行）

- **第 0 波（已在进行）**：换源重载 ≈10 分钟**专项修复**（测量 → 定位 → 优化 → 前后对照）；**视角 A** 状态机/生命周期审计。
- **第 1 波**：视角 B（Rust 数据链路 + 耗时剖面）＋ 视角 C（失败与边界注入）。
- **第 2 波**：视角 D（真机主流程巡检）＋ 视角 E（性能剖面，可与 D 合并执行）。
- **第 3 波**：视角 F（iOS 平台差异）；随后按分诊结果滚动派修复批次。

## 五、分诊与闭环

1. 每个猎捕代理返回后，主代理**逐条核对证据**（能否复现、是否与既有台账重复、影响面判断），写入 `REFACTORING_ACTIVE_PLAN.md` 的开放项台账（含编号、证据出处、定级）。
2. 修复批次按【主流程阻断】→【主流程重扰】→【边缘】顺序派发；每批必须：先红后绿测试 +（UI 类）实机验证 + 双日志同步 + CI 绿。
3. 猎捕与修复**不并行同一文件**；同一视角的发现若集中在同一文件，修复合并为一批。
4. 本计划每波结束回填「已完成视角 / 已发现缺陷数 / 已修数 / 新开项」，保持可交接。

## 六、风险与边界

- 真机巡检可能污染设备状态（种书/改源/删书）→ 要求每轮记录基线并**清理还原**；共享实机档写入类操作前确认无其它任务在用。
- 性能类问题需区分「我方实现慢」与「站点慢」→ 必须给分阶段计时证据，禁止把站点慢记成我们的缺陷（也不得反过来放过）。
- 猎捕不得改动生产代码（只写测试/证据）；发现即登记，修复另派。
